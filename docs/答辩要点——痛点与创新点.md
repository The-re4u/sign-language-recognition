## 一、场景可迁移性

本系统核心架构与场景**强解耦**——语义映射层（JSON配置）+ LLM Prompt（JSON配置）决定了上层行为，底层手势识别管线完全通用。

| 场景 | 语义层适配 | 示例语义链 |
|------|----------|-----------|
| **医院导诊**（当前） | 病症层+身体层+医院操作层+程度层 | "头疼严重持续3天" → AI追问 → 推荐神经内科 |
| **智能家居** | 设备层+动作层+房间层 | "打开客厅灯" / "空调调到26度" |
| **银行柜台** | 业务层+金额层+证件层 | "取款五千元" / "修改密码" |
| **车站/机场** | 交通层+时间层+目的地层 | "买明天去北京的高铁票" |
| **政务大厅** | 政务层+材料层+身份层 | "办理身份证更新" / "提交社保材料" |
| **日常沟通** | 常用语层+情感层+数字层 | "你好，我想要一杯水，谢谢" |

**迁移方式**：替换 `config/semantic_chains.json` + `config/hospital_chains.json` + DeepSeek Prompt 即可。底层 MediaPipe → GCN → TCN → SentenceRecorder 完全不动。

## 二、三大痛点与项目应对

### 痛点 1：为什么不用键盘打字，而用手语/手势输入？

> "打字对听障人士来说是'外语'——他们需要经历'手语思维→汉语语法→字符编码'的双重转换。"

**问题本质**：
- 先天性听障人群的**第一语言是手语**，不是汉语文字
- 打字要求他们将手语概念**翻译成语法不同的汉语**，再**逐字编码成拼音/笔画**
- 认知负荷 = 翻译 + 语法转换 + 字符编码，三重叠加
- 对于老年听障人群，**手语是唯一熟练的语言系统**，打字本质上是用"外语"沟通

**本项目的应对**：
- 手语/手势作为**直接输入接口**，跳过文字编码层
- 17 种手势 → 70 语义槽位 → 自然中文句子，从手势到语义直接映射
- 手势编码比拼音输入更符合手语使用者的认知习惯

**答辩话术**：
> "听障人士的第一语言是手语，不是汉语文字。逼他们打字相当于逼一个中国人用英文写日记——技术上能做到，但认知负荷极高且表达会失真。我们做的是让机器学会'听'手语，而不是让听障人士学会'写'汉语。"

---

### 痛点 2：为什么用 SlowFast TCN 而不是 Transformer？

> "Transformer 更'先进'，但先进 ≠ 适合。"

| 维度 | SlowFast TCN (本项目) | Transformer (ViT/Swin) | 为什么选 TCN |
|------|----------------------|------------------------|-------------|
| 参数量 | 0.7M | 10M+ (ViT-Base) | 任务书要求 <10M，TCN 轻一个数量级 |
| 训练数据需求 | 千级样本可训练 | 通常需万级以上 | 自采集 1,311 条，Transformer 会严重过拟合 |
| 推理速度 | 纯卷积，ONNX 友好，~5ms | 自注意力 O(T²)，~50ms+ | 实时系统要求 <500ms 端到端延迟 |
| 因果性 | 因果卷积，天然无未来帧泄漏 | 需要因果掩码改造 | 手语识别是实时任务，不能偷看未来帧 |
| 多尺度建模 | Slow+Fast 双路径，感受野 43 帧 | 需额外设计多尺度 | Slow 路径捕获 1.7 秒手势短语，Fast 保留细节 |
| 部署 | CPU 可运行，无需 GPU | 通常需要 GPU | 系统设计目标：普通 RGB 摄像头 + 笔记本即可 |

**答辩话术**：
> "Transformer 是更好的模型，但不是更适合这个任务的模型。1,311 条数据上训练一个 10M 参数的 Transformer，结果会是什么？过拟合到 90% 训练准确率、30% 测试准确率。而 0.7M 的 SlowFast TCN 在我们的数据上做到了 82.8% 测试准确率——不是因为它'更强'，而是因为它和这个任务的数据规模、实时性要求更匹配。"

---

### 痛点 3：为什么不用现有公开手语数据集？

> "不是不想用，是没得用。"

**问题本质**：
1. **任务书允许自采集**："收集**或**使用公开手语数据集"——"或"字表明二选一即可
2. **公开数据集不支持双手编码**：WLASL/MS-ASL 标注范式是"单手势→单词"，我们的核心创新（左手模式 + 右手内容 = 70 槽位）在现有数据集中**不存在**
3. **场景词汇不匹配**：公开数据集是通用手语词汇（ASL/CSL），我们的系统是**场景化语义输入**——医院导诊的"挂号/输液/腹泻/呼吸困难"不在 WLASL 里
4. **自采集更严谨**：域随机化（3光照×3角度×3距离）+ 合成增强（遮挡30%/低光照40%/关键点抖动）——这是**受控实验设计**，比用不可控采集条件的公开数据集更科学

**答辩话术**：
> "公开手语数据集标注的是'单词→手势'，我们做的是'双手组合编码→语义槽位'——左手选词类、右手选具体词，17 种基础手势组合出 70 个语义槽。这种编码协议在现有数据集中根本不存在。而且任务书写的很清楚——'收集或使用公开数据集'，'或'字就是我们自采集的依据。"

## 三、创新点总结

### 创新 1：双手组合编码协议

- **左手=模式、右手=内容**，7 层×10 内容=70 语义槽位
- 模式/内容双集合互斥 + 控件手势（双手 Victory/Seven/One）内嵌于语义手势集
- 零歧义、无需额外硬件
- **论文对应**：第三章 3.6 语义解析层

### 创新 2：规则/DL 双模式互补架构

- 规则引擎（XAI）：关节角度>165° + PIP/MCP 双通道，97.6% 合成F1，<1ms
- DL 多模态（SpatialGCN+Visual+Motion+Fusion+TCN）：82.8% 真人准确率，3.4M 参数
- 两者互补：规则处理标准条件，DL 在退化条件下（遮挡/低光照/高速运动）更鲁棒
- **论文对应**：第三章 3.5 + 第四章 4.3-4.5

### 创新 3：多模态轻量化特征融合（v6.0 升级）

- **三模态**：Image(MobileNetV3 CNN, RGB手部ROI) + Skeleton(SpatialGCN + 29维几何描述子) + Semantic(对比学习原型)
- **GatedFusion 门控融合**：逐维学习 gate = σ(MLP([cnn; geo]))，每维独立判断"信纹理还是信几何"
- **E6 主力模型**：7.3M参数，同用户99.2% / 跨用户97.8% / 混淆对89.6%
- **消融完整链**：纯GCN(90.2%) → +CNN裸奔→跨用户崩盘(67.8%) → +几何→恢复(95.6%) → +门控(94.4%) → +语义(97.8%)
- **论文对应**：第三章 3.3-3.5 + 第四章消融实验

### 创新 4：场景可迁移架构

- 语义映射 JSON 配置 + LLM Prompt JSON 配置
- 底层手势识别管线完全通用，上层语义链按场景定制
- 医院导诊 → 智能家居 → 银行 → 车站，零代码修改
- **论文对应**：第四章 4.7 讨论

### 创新 5：从手势到自然语言的完整闭环

- 手势 Token → 最长后缀匹配语义链 → SentenceRecorder 状态机 → DeepSeek 润色
- 导诊模式下支持多轮 AI 追问 → 科室推荐
- 同类系统多止步于手势分类，本系统实现了完整的语义理解+语言生成
- **论文对应**：第三章 3.6-3.7

## 五、预期答辩提问与应答

| 问题 | 应答 |
|------|------|
| "为什么不用 Transformer？" | 数据量不够(1,311条)，Transformer 会严重过拟合；TCN 0.7M vs ViT 10M+，因果卷积天然支持实时推理 |
| "DL 准确率 82.8% 够用吗？" | 规则引擎兜底+DL 互补；同类系统 MSE-GCN 在 WLASL-100 上 85.3%，我们在 1/10 的数据量下做到 82.8%，效率比更高 |
| "和 SignGemma/Google 方案比？" | SignGemma 4B 参数云端 ASL→English；我们是 3.4M CPU 实时 + 导诊闭环，定位不同 |
| "为什么自创手势不用公开数据集？" | 双手编码协议无现成数据集；任务书"收集或使用"允许自采集；域随机化比公开数据集更可控 |
| "有没有真实用户测试？" | 概念验证阶段，工具链就绪，用户研究列为未来工作。Wagh(2025)的方法论提供了临床级验证框架 |
| "场景迁移怎么实现？" | 语义映射 JSON + Prompt JSON，上层替换配置，底层不变。有 65 条医院链模板，新场景按同样格式写 |
| "FPS 够实时吗？" | 检测 31.7FPS > 任务书 25FPS。DL 异步推理不影响主帧率，规则引擎 <1ms |
| "创新点总结？" | 五个：双手编码、规则/DL双模、多模态轻量融合、场景可迁移、手势→自然语言闭环 |
